# 第 7 讲实践篇：双入口的作答与判定

本篇记录[第 7 讲讲义](lecture-7-process-transport.md)五道小测的作答与判定，并给出双入口代码与实测。讲义只留题目，批改放在这里。

| 文件 | 作用 |
|---|---|
| [mini-harness/lecture-7/harness_core.py](../../mini-harness/lecture-7/harness_core.py) | 共享核心与允许调用的清单。三个业务函数、本地描述、按清单查表的 dispatch、未知 endpoint 与坏参数的错误信封。 |
| [mini-harness/lecture-7/connection.py](../../mini-harness/lecture-7/connection.py) | Connection 独占 rpcId 与信封。进程内载体直接查表，远程载体走本地 HTTP POST，业务函数不认识载体。 |
| [mini-harness/lecture-7/cli.py](../../mini-harness/lecture-7/cli.py) | 命令行入口。解析位置参数，结果写 stdout，诊断写 stderr。 |
| [mini-harness/lecture-7/remote.py](../../mini-harness/lecture-7/remote.py) | 本地 HTTP 入口。把同一份清单映射成 endpoint，处理一次 POST。 |
| [mini-harness/lecture-7/demo.py](../../mini-harness/lecture-7/demo.py) | 四个场景对应讲义四条动手任务，输出清单、stdout 纪律、载体替换与未知 endpoint 对照。 |

五个文件只用标准库，离线运行。命令是 `cd mini-harness/lecture-7 && python3 demo.py`。

## 小测批改

### 第 1 题：为什么共用一个启动器

**题目。** 为什么要让所有产品形态共用一个启动器和 profile，而不是每种形态一个可执行程序？说出第二套生命周期带来的两个具体问题。

**正确答案。** 每种形态各自读配置、装插件、决定关闭顺序，会绕开 profile 这条唯一装配路径，形成第二套生命周期。由此带来三个具体问题。装到 profile 里的插件到不了专用 bin。它的行为会和 base 应用偏离。调用方要学一套任意的进程参数，而不是产品的组合模型。DSH 的答案是所有受支持的 Node 应用都从同一个 `dsh` CLI 加具名 profile 启动。

**当时的回答。** 每种产品形态写一个自己的可执行程序，各自读配置、各自装插件、各自决定关闭顺序。看起来直接，实际上会形成第二套生命周期。带完整配置树的专用 bin 会在 profile 启动之外形成第二套生命周期。装到 profile 里的插件到不了它。它的行为会和 base 应用偏离。SDK 调用方还得学一套任意的进程参数，而不是产品的组合模型。

**判定。** 正确。三个具体问题都列出来了，比题目要求的两个还多一个。补一层因果就完整：这三条问题共用一个根因，就是绕开了 profile 这条唯一装配路径，不是 bin 本身写得不好。本题为原文复述。

### 第 2 题：协议入口的三条纪律

**题目。** 协议 profile 为什么要把 stdout 留给协议帧？headless 模式怎么处理推理内容和最终结果？

**正确答案。** 调用方在等一个 JSON-RPC 帧时，进程若往 stdout 写日志，这一句日志就毁了整个协议流。三条纪律是 stdout 只放协议帧，给人看的内容走 stderr，协议 profile 不热重载服务器模块。headless 把推理增量写到 stderr，只在 stdout 打印最终文本。最后一个终止原因为 `completed` 时退出码为 0，否则为 1。没有任务是用法错误。

**当时的回答。** 逐条复述了讲义。进程形态一多最先出问题的是输入输出通道。调用方在等一个 JSON-RPC 帧，进程却往 stdout 写了一句日志，这一句日志就毁了整个协议流。第一条 stdout 只放协议帧，显示帮助时不启动 transport，stdin 收到 EOF 或收到信号时通过有界根节点 dispose 收尾。第二条给人看的内容走 stderr，推理增量写 stderr，stdout 只打印最终文本，终止原因是 completed 时退出码 0，没有任务是用法错误。第三条协议 profile 不热重载服务器模块，SDK 和 ACP 无法在一个 stdio 连接内安全替换服务器、agent、持久化或工具注册表，配置变更的采用边界是进程重启。还补了信号语义，第一次 SIGINT 或 SIGTERM 优雅排空，插件树最多 5 秒 dispose，第二次立即强制退出，并联系到第 2 讲的 disposer 逆序清理。

**判定。** 正确，有一处边界要澄清。三条纪律和 headless 的两个输出通道都答到了。需要澄清的是「配置变更的采用边界是进程重启」这句。它只对 SDK 和 ACP 成立，对 web 不成立。web 的配置层仍然热重载，关闭的只是服务器模块替换。这两个概念要在记忆里分开。本题为原文复述。

### 第 3 题：消费端投影的三条规定

**题目。** 消费端投影为什么只暴露标记过的方法，描述信息为什么不上线路？

**正确答案。** 手写客户端接口会和 Host 签名、lookup ID 与 schema 漂移，也不能保证只包含 Remote 标记的方法。所以从 Host 代码生成消费端投影。投影只暴露标记过的方法，消费端的类型集合由 Host 声明决定。描述方法的信息只在两端本地，线路上只有 endpoint 和具名参数对象。如果描述随请求上线路，消费端就能自己声明一个不存在的 endpoint，Host 还得解释它。业务类型也只有一份，消费端不复制 DTO。

**当时的回答。** 复述了手写接口的漂移问题和三条规定的原文，并在第二条后面补了一段推理：如果描述随请求一起发，消费端就能自己声明一个不存在的 endpoint，Host 还得解释它。现在两端各自持有一份从同一份源码生成的描述，不一致在构建期就暴露。

**判定。** 正确。三条规定齐全，而且补上的因果推理是讲义里没有强调的部分。这是五题里唯一有独立推理的一题。本题主体为原文复述，末尾推理为自主作答。

### 第 4 题：远程调用的边界

**题目。** 一次远程调用从消费端方法到 Host 业务方法经过哪些层？哪一层独占物理连接，它为什么不把 `fetch` 暴露给上层？

**正确答案。** 调用链是消费端 descriptor 组装具名参数，合并取消信号，经 `ctx.connection.rpc.call` 交给 Connection，Connection 创建 rpcId 和 envelope，载体发出 HTTP 请求，Host 侧做信任检查并交给 Gateway，Gateway 解码、解析 receiver、注入信号、调用业务方法，最后按同一个 rpcId 回送结果。独占物理连接的是 Connection。它不把 `fetch` 暴露给上层，是因为一旦 request 对象进入 Remote 层，物理对象就穿透了边界。将来从 HTTP 迁到 WebSocket 时，改动会扩散到所有上层消费方。现在载体替换只改 Connection 内部。

**当时的回答。** 第一轮只抄了完整调用链，从 `ctx.remote.goals.create` 到 Connection 按 rpcId 回送，没有回答后面两问。

**判定。** 第一轮不通过。漏答「哪一层独占物理连接」和「为什么不暴露 fetch」两问。把边界取舍题当成了流程记忆题。

**重做回答。** 独占物理连接的是 Connection。它注册 `/api` 的唯一 route，持有 RPC envelope、rpcId、序列化和错误传输。不把 fetch 暴露给上层，是因为一旦 request 对象进入 Remote 层，物理对象就穿透了边界。将来从 HTTP 迁到 WebSocket 时，改动会扩散到所有上层消费方。现在载体替换只改 Connection 内部。

**重做判定。** 通过。两层边界都说准了。这段是按批改给出的判定复述，逻辑正确，但还需要一个变式验证才算掌握。变式问法是：以后要把 HTTP 换成 stdio 载体，按这个边界要改哪几处？正确答案是只改 Connection 内部。能立刻答出，说明是真理解而不是记住了这句话。

### 第 5 题：双入口的平台取舍

**题目。** 平台取舍题。你的 mini-harness 要同时提供命令行和本地 HTTP 两个入口。你会怎么切启动层、方法清单和物理连接，哪些机制可以先不做？

**正确答案。** 启动层用一个统一入口加 profile，两个入口共用同一份核心组合，不写两个 bin。方法清单是一张允许跨入口调用的清单，进程内实现直接查表，远程实现走 RPC 信封，业务函数只认清单里的 endpoint。物理连接单独一层独占载体，业务函数不碰 HTTP。可以先不做的是类型投影生成器、WebSocket mux、心跳、断线重连、snapshot 恢复和双工流。判断标准沿用第 6 讲，出现第二个入口再切，不要预防性把协议做全。

**当时的回答。** 第一轮答了入口只解析参数和装配载体，跨入口调用统一走 `invoke(endpoint, args)`，stdout 纪律写进代码，允许调用的方法用小注册表显式声明。还答了先不做的四项机制，以及「出现第二个入口再切」的判断标准。没有按题目要求分启动层、方法清单、物理连接三段作答，漏了启动层怎么切和物理连接怎么切。

**判定。** 第一轮部分通过。统一调用形状和判断标准都答对了，但两段必需的切法缺失。「小注册表显式声明」是方法清单的实现方式，替代不了启动层和连接层的切法。

**重做回答。** 一个统一启动入口加 profile，两个入口共用同一份核心组合，不是写两个 bin。单独一层独占载体，业务函数只声明 endpoint，不碰 HTTP。经提示后补上两段：方法清单怎么切是两个入口共用一张允许调用的清单，进程内实现直接查表，远程实现走 RPC 信封，业务函数只认清单里的 endpoint。先不做哪些是类型投影生成器、WebSocket mux、心跳、断线重连、snapshot 恢复、双工流。

**重做判定。** 通过。启动层、方法清单、物理连接三段齐全，先不做的机制也列全了。

## 动手：跑通四个场景

四个场景对应讲义的四条动手任务。下面是 `python3 demo.py` 的实际输出。

### 场景 1：共享核心与一份允许调用的清单

```
==============================================================
场景 1：共享核心与一份允许调用的清单
==============================================================
  两个入口共用同一份清单，业务函数不认识载体
  [allowed] sessions/create(title)
  [allowed] sessions/prompt(sessionId, text)
  [allowed] sessions/list()
      [conn] rpc-1 -> sessions/create args={'title': 'demo'}
  [direct] {"rpcId": "rpc-1", "ok": true, "result": {"sessionId": "s-1", "title": "demo"}}
```

清单只有一份，写在 `ALLOWED` 里。每项记着 endpoint、参数名和处理函数。这就是骨架版的 `@Remote` 标记。直接调用时 Connection 也照常生成 rpcId，把请求交给进程内载体，和远程路径共用同一个调用面。

### 场景 2：命令行入口与 stdout 纪律

```
==============================================================
场景 2：命令行入口解析参数，结果只写 stdout
==============================================================
  [exit] 0
  [stdout] {"sessionId": "s-1", "reply": "已收到 'hi'", "turns": 1}
  [stderr] [conn] rpc-1 -> sessions/prompt args={'sessionId': 's-1', 'text': 'hi'}
  → 诊断与结果分通道，stdout 可以直接被下游解析
```

stdout 只有一行 JSON，可以被下游直接解析。诊断写到 stderr。这一点是实测跑出来的。第一次实现时我把 Connection 的 `[conn]` 日志写到了 stdout，结果这一行混进了结果通道。发现后改成写 stderr，才得到上面这份输出。这正是讲义第三条纪律里「stdout 只放协议帧」的具体含义。

### 场景 3：换载体不改业务

```
==============================================================
场景 3：HTTP 入口把同一份清单映射成 endpoint
==============================================================
      [conn] rpc-1 -> sessions/list args={}
  [reply] {"rpcId": "rpc-1", "ok": true, "result": {"sessions": [{"sessionId": "s-1", "title": "demo", "turns": 1}]}}
  → 业务函数与清单没改，换的只是 Connection 的载体
```

两个入口用的是同一个 `Harness` 实例。场景 2 通过 CLI 写入的一轮对话，在场景 3 通过 HTTP 读取时已经能看到。会话状态只存一份。换载体时改的是 `RpcCarrier`，`harness_core.py` 一行没动。

rpcId 由 Connection 构造并随信封送到服务端，响应里原样带回。远程载体只封装 HTTP 细节，不把 `request` 对象交给业务函数。

### 场景 4：未知 endpoint 的报错对照

```
==============================================================
场景 4：未知 endpoint，两种入口的报错对照
==============================================================
  CLI   exit=1 stdout=''
  CLI   stderr [conn] rpc-1 -> nope/run args={} | [unknown/endpoint] endpoint 'nope/run' 不在清单里
      [conn] rpc-1 -> nope/run args={}
  HTTP  {"rpcId": "rpc-1", "ok": false, "error": {"code": "unknown/endpoint", "message": "endpoint 'nope/run' 不在清单里"}}
  → 清单是唯一裁决点，两个入口都拒绝同一个 endpoint
```

两个入口给出同一个错误码 `unknown/endpoint`。差别只在通道。命令行写 stderr 并以 1 退出，stdout 为空。HTTP 把错误装进信封返回。清单是唯一裁决点，入口只是把裁决结果送到不同的地方。

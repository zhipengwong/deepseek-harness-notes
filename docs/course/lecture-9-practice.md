# 第 9 讲实践篇：平台取舍的作答与判定

本篇记录[第 9 讲讲义](lecture-9-platform-tradeoffs.md)五道小测的作答与判定，并给出一份取舍清单示范。讲义只留题目，批改放在这里。

这一讲不产出课程代码。前面八讲的代码已在 `mini-harness/lecture-0/` 到 `mini-harness/lecture-8/`，本讲只用它们作参照。下面是批改与通用清单示范。

## 小测批改

### 第 1 题：清单还是代码

**题目。** 为什么收官讲的产出是清单而不是代码？说出一个平台比 harness 多出来的约束。

**正确答案。** 不给代码有两条理由。平台的后端选择因人而异，写死的骨架只会误导。取舍是判断，不是实现，判断错了代码写得再漂亮也是沉没成本。平台比 harness 多三样东西，多用户、任务并发、故障要有人兜底。harness 里一个假设在一个任务上成立，放到几十个任务同时跑就会破。

**当时的回答。** 两条理由都用自己的话答到了。写的是平台底座各不相同，数据库选型、RPC 框架、鉴权体系、存量微服务都不一样，不存在能复制粘贴的万能平台代码。第二条写落地难点在取舍与排期而非语法实现，清单提供判断标尺与准入门槛。平台多出来的约束给了多租户与跨请求隔离，包括多用户高并发、无状态实例调度、跨租户数据权限隔离、会话在 Worker 间漂移的状态一致性，还补了配额计费、审计合规、外部 SLA 超时。

**判定。** 通过。两条理由都答到，而且不是原文复述。"后端底座各不相同，不存在万能平台代码"对应"后端选择因人而异，写死的骨架只会误导"，"取舍是判断不是语法实现"对应"判断错了代码再漂亮也是沉没成本"。平台约束给到四项，超过题目要的一项。

### 第 2 题：三条不变量的失效

**题目。** 事实源、顺序、失败关闭这三条为什么没有商量余地？各说一句它在平台上对应的失效。

**正确答案。** 三条是平台能不能被信任的底线，不是性能优化项。缺任何一条，规模上去之后都是信任问题，不是功能问题。事实源要求模型可见事实先落成日志再派生请求，平台里翻译为谁在什么时候让 agent 做了什么必须能回答。顺序要求先入日志再分派工具、先派生请求再发模型调用，倒过来得到孤儿结果和因果倒置的日志，审计就是假的。失败关闭要求没人认领的请求一律拒绝、被拒工具也落成规范结果，平台里翻译为权限边界，宁可少做一次不可越权一次。

**当时的回答。** 为什么没有商量余地答到了核心，写这三条决定数据正确性与可恢复性，破坏后是静默数据腐烂和不可逆外部副作用，不是性能下降，事后无法通过加机器或打补丁挽回。三条对应失效都给了讲义里没有的具体场景。事实源写 A 节点内存拼系统提示词未落日志，请求超时由 B 节点接管恢复，B 节点缺上下文导致推理断裂、重复提问或自相矛盾。顺序写模型流式输出未结算就并发派发支付或改库工具，随后断流或 Worker 重启，恢复时以为未执行而重复触发写操作。失败关闭写下游工具超时或网关断连未做失败闭合与状态落盘，会话永久卡在工具等待中，后续新消息全部触发协议校验报错。

**判定。** 通过，本轮答得最好的一题。三条失效场景是自己推的，讲义里没有，而且准确。

有一处边界补充，不改变判定。讲义里失败关闭的落点是审批闸门，平台翻译是权限边界。当时回答写的孤儿任务与悬挂死锁，是工具超时断连后的未闭合修复，属于崩溃恢复侧的失败关闭。两者都是失败关闭，落点不同。要记住失败关闭有两个落点，审批侧的越权和恢复侧的悬挂。

### 第 3 题：三个放大问题

**题目。** 平台侧的三个放大问题是什么？每个说一句它的代价。

**正确答案。** 讲义定义三个放大问题。隔离是一个任务一个沙箱，带超时、内存上限、网络出口白名单，凭据由运行时注入短时令牌，代价是每个任务多一次环境准备，高任务量时算进成本。幂等是同一业务单据重复投递不重复执行，任务与回写都要幂等键，代价是每条链路多一次查重、多一张状态表。可回放的证据链是每条处理落一条记录，输入快照、工具轨迹、输出、判定、成本，能按同样输入重跑，代价是存储增长，需要保留期和压缩策略。

**当时的回答。** 第一轮答的是存储与状态竞争、上下文膨胀与推理成本、外部副作用与故障传播。这三个都是真实的平台问题，讲得也对，但不是讲义定义的三个放大问题，答的是另一个框架。第一轮不通过。

**重做过程。** 第二轮把第一轮的三段原文逐字重贴，仍是那三个问题，判定不通过。第三轮按讲义的三个名字重写，隔离的代价写资源冗余、共享复用率下降、缓存与连接池碎片化、跨上下文协作的编排开销。幂等的代价写状态存储与去重校验的延迟、维护幂等键与结果快照、接口显式设计确定性执行键的改造成本。证据链的代价写全量落盘的存储与 I/O 吞吐损耗、同步序列化与 flush 屏障的写放大、Schema 契约演进包袱。

**重做判定。** 第三轮通过。三个名字对了，代价方向全部对上讲义，隔离落在资源开销，幂等落在状态存储与接口约束，证据链落在存储 I/O。三条都做了自己的扩展，缓存连接池碎片化、确定性执行键、Schema 演进包袱是讲义里没有的自主推理。

### 第 4 题：先补还是先等

**题目。** 判断一个机制先补还是先等的标准是什么？举一个先补的例子和一个先等的例子。

**正确答案。** 标准是一句话，缺了会出事或者一定会换的先补，只有一种实现或者判断不明的先等。先补三类，不变量相关的事实源、顺序、失败关闭，缺了会出事的隔离和幂等，一定会换的后端要现在切 seam。先等两类，只有一种实现的机制不做预防性拆分，判断不明的先记下来等真实任务暴露。

**当时的回答。** 用自己的框架给了判断标准，看机制保护的是系统正确性与不变量，还是吞吐效率、成本与高阶扩展形态。先补的是违反三大铁律的缺口，以及事后补救需要停机洗数据的底层数据结构问题。先等的是当前规模未触发真实瓶颈、未来能增量叠加且不用推翻日志协议的机制。先补例子给带单写者锁与 flush 屏障的 append-only 日志落盘，理由是事实源与顺序的根基，初期图省事存内存数组或异步写库不等待确认，重启或恢复就丢数据或乱序，后期没法迁移。先等例子给多代理派生调度与精细化的 Surface 替换压缩，理由是初期单代理线性循环加纯追加投影足以正确完成任务，还天然命中 KV Cache，等上下文溢出或 Token 超标再增量引入，不破坏原有日志结构。

**判定。** 通过。标准、先补例子、先等例子齐全，理由充分，用的是自己的抽象框架。

有一处补充，不改变判定。先补的第三类"一定会换的后端，现在就切 seam"在当时的二分法里没有明确位置。它可能被归到高阶扩展形态先等，但讲义要求先补。差别在于 seam 保护的是改造成本，现在不切将来要付扩散代价，它既不完全是正确性也不完全是性能，是独立的第三类。

### 第 5 题：极简平台的取舍

**题目。** 平台取舍题。你手上的平台现在只有一个入口、一种模型、一个用户。按这一讲的标准，你会把哪些机制写进"现在补"，哪些写进"等条件"？说出至少一项的判断理由，并指出一个会让你改变决定的触发条件。

**正确答案。** 极简约束下并发竞争、多租户隔离、多模型路由的复杂度归零，决策极度克制，只守底线。现在补的是事实源、顺序、失败关闭三条不变量对应的最小机制，事实源用 append-only 事件日志落盘，顺序用先入日志再派生再调用的基础循环，失败关闭用退出刷盘与未闭合事件的尾部修复。等条件的是只有一种实现或判断不明的机制，分布式锁、多模型适配、压缩策略、动态插件化都等真实触发再补。判断标准是缺了会出事或一定会换的先补，只有一种实现或判断不明的先等。

**当时的回答。** 现在补三项。单一事实源的事件日志，定义最小事件类型 user、assistant、tool_call、tool_result、turn_end 并落盘，哪怕先用本地 SQLite 或 JSONL。严格的因果顺序与基础 AgentLoop，强制先写事件入日志、再投影组装提示词、调模型或执行工具，并设置最大循环步数上限。失败关闭与退出刷盘，进程退出或单轮异常中断时完整刷盘，重启发现未闭合 tool_call 自动补错误闭合事件。等条件四项。分布式锁与多实例状态同步，等出现多进程或多入口并发。多模型适配器与路由降级，等接入第二家模型厂商。Surface 替换压缩与摘要算法，等频繁触及上下文上限或 Token 超标。动态插件热插拔微内核与复杂权限沙箱，等工具激增、多人协作开发。判断理由选跳过动态插件化与复杂压缩但坚持事件日志与失败关闭。单用户单入口没有多团队并行开发摩擦，硬上动态插件树增加心智负担，单模型直接透传消息结构最大化利用厂商 Prefix Cache。但事件日志与失败关闭不能省，调试时一次 Ctrl+C 强杀或网络断连，没有 flush 和尾部修复就会导致会话文件损坏或工具重复执行。触发条件给了两个。人数或入口变化，开放第二个并发用户或新增定时任务与 Webhook 入口，就把本地单文件存储升级为带锁的数据库并补齐租户权限边界。任务长度变化，单次任务平均超过 20 步或上下文频繁突破 64K Tokens，就引入 Surface 替换压缩与工具输出截断。

**判定。** 通过，全轮最好的一题。现在补、等条件、判断理由、两个触发条件都齐，而且触发条件写成可证伪的阈值，符合讲义"依据那一列必须写触发条件"的纪律。判断理由选得准，单用户硬上插件树是负担，但一次 Ctrl+C 就能暴露日志与失败关闭的缺失。

有一处事实纠正，不改变判定。当时回答写"设置最大循环步数上限"。作为自建平台的设计选择可以加这个上限，但 DSH 源码没有它。第 3 讲和第 8 讲都确认过，循环没有内置轮次预算，限制失控任务要从既有生命周期扩展点执行取消。把"我要加"当成自己的取舍没问题，但不要误认为是 DSH 的做法。

## 总评

五题最终全通过。这一轮是九讲以来作答质量最高的一轮，多数答案用自己的框架，不是原文复述。第 1、4、5 题第一轮就通过，第 2 题的三条失效场景全部是自推。

唯一反复的是第 3 题。第一轮答成另一个框架的三个问题，第二轮又逐字重贴第一轮原文，第三轮才按讲义的三个名字重写。问题不在理解，在读题。题目要的是讲义定义的三个放大问题，不是自己熟悉的另一个框架。这个错误和第 8 讲答错接缝是同一类，框架选错，内容再对也不计入本题。

两处边界要记牢。失败关闭有两个落点，审批侧的越权和恢复侧的悬挂。先补有第三类，一定会换的后端要现在切 seam，它不属于正确性与性能任何一类。

独立推理集中出现。第 2 题的三条平台失效场景，第 4 题的正确性与扩展二分法，第 5 题的可证伪触发条件与 Prefix Cache 理由，第 3 题重做里的确定性执行键与 Schema 包袱，都是讲义里没有的内容。这说明八讲的机制读进去了，能往平台场景推。

这一讲是收官讲。五题考的不是机制细节，是把判断标准用在自己的场景上。能定出触发条件，清单才从原则变成决定。

## 动手：一张通用清单示范

下面是按讲义五列写法填的一份通用清单。平台场景取一个准备自建 Agent 平台的普通团队，只有一个命令行入口、一种模型、一个用户。这是教学示范，不是任何具体平台的设计结论，也不带入私有系统信息。针对自己平台的具体清单在对话里单独给，不写进仓库。

### 任务一：八讲机制逐行填表

平台现状只准写已经有、部分有、没有三选一。

| 机制 | 解决的失效 | 平台现状 | 决定 | 依据 |
|---|---|---|---|---|
| 第 4 讲 Session 日志 | 崩溃后记忆丢失、无法回放与审计 | 没有 | 现在补 | 第一个真实任务上线前就要有，单用户本地也要防强杀损坏会话 |
| 第 3 讲 循环与状态机 | 长任务无人终止、取消不传播 | 部分有，仅单轮调用 | 现在补 | 任务引入工具调用后必须有取消与挂起终止，否则一次超时就悬挂 |
| 第 5 讲 工具闸门 | 越权执行、审批绕过 | 没有 | 现在补 | 第一个会写本地文件的工具接入前，失败关闭必须就位 |
| 第 8 讲 整合装配 | 装配顺序与关闭顺序无人保证 | 部分有，靠手工初始化 | 现在补 | 统一入口保证按序创建、逆序关闭，先于多机制叠加 |
| 第 6 讲 能力 seam | 换后端时改动扩散到全部调用方 | 没有 | 等条件 | 等接入第二家模型厂商或第二种执行载体再切 |
| 第 2 讲 插件化 | 加功能要改内核 | 没有 | 等条件 | 等有两个以上团队并行开发不同工具再引入插件树 |
| 第 7 讲 进程与通信 | 多入口、跨进程调用 | 部分有，一个 CLI 入口 | 等条件 | 等出现第二个入口或跨进程调用方，再切 Connection 与载体 |
| 第 0、1 讲 调用与循环 | 模型只输出文本、工具要程序执行回灌 | 已经有，单次 SDK 调用 | 不做 | 单次调用已覆盖，多轮工具任务由第 3 讲循环承担，不重复建层 |

### 任务二：三行现在补，逐行写触发条件

决定为现在补的，依据必须写出触发条件，不能只写重要。

1. Session 日志。触发条件是第一个真实任务上线。哪怕单用户本地，也要防一次强杀或断连把会话文件写坏。
2. 基础循环与取消。触发条件是任务第一次引入工具调用。有工具就可能在等待里悬挂，必须有终止与取消传播。
3. 工具闸门。触发条件是第一个会改外部状态的工具接入。写文件、发请求这类工具接入前，失败关闭要就位。

### 任务三：两行不做，写放弃理由

决定为不做的，理由里要指出什么条件下重新考虑。

1. 第 0、1 讲的单次调用层单独建库。放弃理由是现有 SDK 调用已覆盖文本生成，多轮任务交给循环层，单独再建一层只会重复。重新考虑的条件是出现 SDK 覆盖不了调用形态，比如要直接控制流式分片或自定义报文。
2. 第 7 讲的进程边界。放弃理由是当前只有一个 CLI 入口，没有跨进程调用方，切 Connection 是提前付成本。重新考虑的条件是出现第二个入口，比如本地 HTTP 或 Webhook。

### 任务四：把清单交给不了解课程的人反驳

选做。把上面清单给一个不了解课程的人看，请他圈出依据不足的行。检查三条。现在补的行，触发条件是不是真会发生的事件，还是"重要"这类空话。等条件的行，等的是什么是不是可观测的信号，比如第二个模型厂商、第二个入口。不做的行，重新考虑的条件是不是具体。圈出来的行要么补依据，要么把决定改成等条件或不做。反驳不掉，才说明清单经过了自己的场景。

## 事实边界

三条不变量对应的源码事实来自本地源码副本的子系统文档与架构笔记，基线 commit `4b399c39`。事实源、顺序、失败关闭、不要预防性拆分、日志压缩需求都能在该基线下定位。平台侧的三个放大问题，即隔离、幂等、证据链，来自通用平台工程判断，不是 DSH 源码事实，也不是某个具体平台的设计结论。清单写法与判断标准是教学判断。

上面这份通用清单是教学示范，用一个极简平台场景演示五列写法，不是任何具体平台的规划结论。实测与代码在本讲不产出。小测判定是教学判断，不是源码事实。

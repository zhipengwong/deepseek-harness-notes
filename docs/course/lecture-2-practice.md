## 任务 2：新插件自动收到事件

新增 `echoer` 插件。改动只有两处：定义插件函数，在加载序列里加一行。内核 `plugin_core.py` 与已有插件 `greeter`、`shouter` 一行未动。

```python
def echoer(ctx):
    """任务 2 新增的插件。与另外两个互不认识，只订阅同一事件。"""
    ctx.on("greet", lambda name: print(f"  [echoer] 收到 greet: {name}"))
```

加载后广播一次，卸载 echoer 后再广播一次。

```bash
python3 demo_task2.py
```

实测输出：

```
=== 加载插件 ===
[加载] greeter
  [heartbeat] 启动定时器
  [greeter] 打开连接
[加载] shouter
[加载] echoer

=== 事件广播 emit ===
  [greeter] 收到 greet: world
  [shouter] 收到 greet: world
  [echoer] 收到 greet: world

=== 卸载 echoer 后再广播 ===
  [echoer] 已卸载
  [greeter] 收到 greet: again
  [shouter] 收到 greet: again
```

两个结论。

第一，echoer 没有向内核登记任何东西，也没有改其他插件的代码，广播时它自动收到事件。订阅即注册：插件在自己的 `apply` 里 `ctx.on()`，框架负责把事件送到。加插件不改内核，这是插件化「功能自声明」的实测。

第二，卸载 echoer 用的只是加载时返回的 fiber 引用，没有手写任何清理代码。再广播时只剩两个接收方，echoer 的监听器已随 fiber 撤销。`ctx.on()` 本身就是一个 effect：注册监听器时同步挂上 disposer，卸载时自动移除。

实现细节有一个坑：卸载要用 `App.load()` 返回的 fiber 句柄。框架没有提供按名字查找插件的方法，也不需要——加载时把返回值接住即可。

## 任务 3：第二个 effect 的逆序清理

给 greeter 再加一个 effect（启动计时器），与原有「打开连接」并存。验证两点：新 effect 的清理函数在卸载时执行；多个清理函数之间的顺序。

卸载段实测输出：

```
=== 卸载主插件（子插件随父一起）===
  greeter 卸载前状态: ACTIVE
  [heartbeat] 清理定时器
  [greeter] 停止计时器
  [greeter] 关闭连接
  greeter 卸载后状态: DISPOSED
```

对照加载顺序（heartbeat 启动定时器 → greeter 打开连接 → greeter 启动计时器），卸载正好是镜像。两层顺序都得到验证：

| 维度 | 规律 | 证据 |
|---|---|---|
| 层级 | 子插件先于父插件卸载 | heartbeat 的清理在最前 |
| 时间 | 同一插件内按注册逆序清理 | 先停后注册的计时器，后关先注册的连接 |

对应 `Fiber.dispose()` 里的 `for fn in reversed(self.disposers)`。逆序不是风格偏好：如果插件 B 依赖插件 A 打开的资源，B 后注册、先清理，销毁时就不会用到已被拆掉的依赖。子插件先于父卸载是同一原则在层级维度的体现。

## 选做：waterfall 不调 next() 会怎样

写一个「只想旁观」的 waterfall 监听器，打印日志后 `return None`，不调 `next()`。三个场景对照。

```bash
python3 demo_task4.py
```

实测输出：

```
=== 坏例子：旁观者不调 next ===
  [buggy] 旁听到了: 'hello'（但没有调 next）
  最终结果: None

=== 正确写法：旁观者调 next ===
  [good] 旁听到了: 'hello'，调 next 放行
  最终结果: '<hello>'

=== 对照组：链上没有监听器 ===
  最终结果: 'DEFAULT(hello)'
```

坏例子里链条在旁观者处静默终止：排在后面的 terminal 监听器没有执行，最终结果不是默认值，而是坏监听器自己的返回值 `None`，全程不报错。

对照组给出一个比讲义更精确的结论：`default` 不是「出错保险」，而是「无人接手保险」。只要链上有一个监听器接了手——哪怕忘了传值、返回了 `None`——`default` 就不会执行。忘调 `next()` 的破坏力因此是双重的：掐断下游监听器，同时绕过默认值。讲义的纪律（只观察的监听器必须 `return next(value)`）针对的就是这一点。

## 小测与批改

第 2 讲共五题，前四题作答并批改如下。每题先列题目和正确答案，再记录当时的回答与判定。第 5 题的判断标准已在讲义「五种方式的使用场景」一节给出，留作自测。

### 第 1 题：插件化解决的核心问题

**题目**：插件化解决的核心问题是什么？

**正确答案**：功能不断增长，每加一个都改内核会让内核臃肿、改动互相冲突。插件化把这件事反过来：内核只提供注册机制和生命周期，不认识具体功能；功能自己声明「我提供什么」，加载时注册，卸载时自动撤销。三条收益是功能与内核解耦、插件间通过事件协作互不认识、可独立卸载不留残留；两条代价是间接层变多调试路径变长、加载顺序由依赖决定心智负担上升。

**当时的回答**：完整覆盖问题（内核臃肿、改动冲突）、反转（内核只提供注册机制与生命周期，功能自声明、卸载自动撤销）、三条收益与两条代价。

**判定**：正确。

### 第 2 题：effect 的作用

**题目**：`ctx.effect()` 的作用是什么？为什么外部资源要包起来？

**正确答案**：插件化最难的不是加载，是卸载。通过 ctx 注册 API 建立的东西框架自动跟踪；框架管不到的外部资源用 `ctx.effect()` 包起来，`setup` 在加载时运行，返回的 `cleanup` 在卸载时被调用。人工手写清理代码漏一个就留一个残留，effect 让插件不必自己记着何时清理。

**当时的回答**：覆盖「框架自动跟踪的」与「框架管不到必须手动包的」这一关键区分、`setup`/`cleanup` 的执行时机，以及最小框架的实现（`Fiber.add_disposer()`、逆序清理、子插件先于父插件卸载）。

**判定**：正确。

### 第 3 题：卸载时的执行顺序

**题目**：fiber 卸载时，子插件和清理函数的执行顺序是什么？

**正确答案**：子插件先于父插件卸载；同一插件内的清理函数按注册顺序的逆序执行。

**当时的回答**：初始回答只贴了部分卸载输出，能证明子插件 `heartbeat` 先清理，但缺了第二个 effect 的「停止计时器」一行，没有体现清理函数之间的逆序。补跑 `demo.py` 贴全三行卸载输出后，两层顺序都有证据。

**判定**：补全后正确。

### 第 4 题：waterfall 不调 next()

**题目**：waterfall 监听器不调用 `next()` 会发生什么？这条纪律为什么重要？

**正确答案**：链条在该监听器处静默终止，下游监听器不再执行。只观察的监听器必须 `return next(value)`，否则整条下游链路被吞。

**当时的回答**：复述了机制（不调 `next()` 直接返回时，下游和默认值都被短路，上游称为否决）与纪律原文。

**判定**：正确。补一点来自选做实验的精确化：`default` 只在链上没有任何监听器接手时才兜底；坏监听器返回 `None` 也算「接手」，所以默认值同样被绕过。
